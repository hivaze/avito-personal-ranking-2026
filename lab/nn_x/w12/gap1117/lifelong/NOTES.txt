Why GO [I], in one paragraph: everything except the GPU run is now done and checked. The arrays are built with a leak check on
every event. The patch reproduces the stored predictions bit for bit when the flag is off. Training rows get extensions as
long as test rows do (dose KS 0.09), so the 2.8-day vs 14.2-day snapshot gap that was the parity worry does not show up in
what the model sees. A read restricted to the bucket of extended feeds has power 0.71 at the replay's proxy effect, and its
SE is calibrated by a member-swap null, so the test can answer the question the replay could not ("closed for lack of power").
The cost is 16 re-cools, about 17 GPU-hours, on GPUs that are idle. By the lead's own practice (kw08 / m05 were run at
P(pass) 0.03-0.04), a P(pass) of about 0.26 is worth one run.
Why it is only a small GO [I]: the extension reaches 7.2% of test feeds (private-like 7.0%). Even if all of the replay's proxy
effect is captured, the pool-level gain is about +0.00012..+0.00019 on private. That is below every file-level MDE (val
near-copy 0.00086, public 0.0011). A pass therefore decides the mechanism, not a file. Promotion would need re-cooling the 20
FD16P20 members and their fine-tunes (section 6.4). Expected private gain of the whole route: about +0.00003. Its value is
mostly in closing the question.

Reading [D/I]:
 - The gap problem the refill and the review sized (2.9 vs 14.2 days) does NOT carry over to what the model sees in T
   extensions. A T block is "the events just older than the stored 256th". Its size grows with the gap, but on test a long gap
   also breaks the alignment for heavy users (A fails for 16% on test, 2.6% on train), and the two effects cancel: the dose
   distribution matches at k0 (KS 0.04 on all feeds, 0.09 capped). A k-day restriction makes the dose parity WORSE (KS 0.14-0.24),
   because train snapshots >= k days back carry more events, and it cuts train coverage to 2-6%. Reweighting train by gap
   cannot work: 54.5% of the test mass (gap >= 14 d) has no train counterpart, and the effective sample size is 0.195.
 - The view share of the block (train 0.26, test 0.17) is inherited from the generic train-format difference, which is larger in
   the stored histories themselves (all capped feeds: train 0.53, test 0.38, KS 0.53; val vs test KS 0.008). It is not
   specific to the extension. The --hcap arm that targeted this format difference was null.
 - Uncapped extensions are the one parity-skewed part (8.5% of extended train feeds against 28% of test). Excluded by default.

Design (all OFF at --hist_ext 0. The flag-off cfg and state dict are exactly the old ones, and every flag-off path is the old code):
 - Loader (data.SplitData(hist_ext=128, hist_ext_dir, hist_ext_var, hist_ext_uncapped)): loads ext_* and appends ext_table rows to
   the item table. gather() returns the block as separate keys xe_raw / xemb_ok / xmask / xcat / xet / xes / xidx / Hx (width
   Kx = 64 or 128). When a batch holds an extended feed, the stored block is forced to its full 256 width, so extension token j
   sits at history position 256 + j (positions 257-384 counted from 1). The stored keys (he_raw, hmask, H, ...) are untouched.
 - Dense inputs: dense_features never sees the x* keys. All 104 dense inputs (max / mean / top-3 / per-type cosine, category
   counts, recency of the newest same-category event, log(1 + H), count / H, ...) stay computed on the stored 256 events, and so
   do the 34 precomputed xt columns. T4 verifies dense inputs are identical with and without x* keys.
 - Model (Ranker(hist_ext=128)): new parameter rec_x = nn.Embedding(128, d), the position codes of slots 256..383, built last
   under its own RNG fork. Ranker._hist_view concatenates stored and extension tokens for the TOKEN PATH only: history encoder
   (1 self-attention layer over user + 256 + Kx tokens), the 2 cross-attention blocks with their cosine bias (sim_bias 1), and
   the retrieval.
 - New position rows when re-cooling a checkpoint (train.py --init with --hist_ext): every tensor loads strictly. rec_x is the
   only missing key (asserted) and is initialised by --hist_ext_init:
     row255 (DEFAULT): every extension slot = rec row 255. This is the convention of the refill's untrained pass d1, measured at
       d1 - a = +0.0009 +- 0.0006 pooled, so the re-cool starts from a known, non-harmful point. T3: with row255 and no
       training, extended val feeds move little (score corr 0.99996, top-1 changes in 10% of them).
     shift128: slot 256 + j = rec row 128 + j.  deep_mean: the mean of rows 192-255 rescaled to their mean norm.
   Why not something smoother [M]: the trained rows are not smooth in position (cosine of neighbouring rows 0.33 for rows
   128-254, 0.65 for 0-31; cosine to row 255 of rows 200+ is about 0.2-0.4), so there is no trend to extrapolate.
 - Retrieval of the 16 most similar history items (HistRetrieval, retr_m 16, no de-duplication in the finals): the top-16 is
   taken over stored AND extension events, by raw cosine, with events without a vector excluded as today. The recency bucket
   floor(log2(1 + idx)) already saturates at 8 from position 255, so extension events share bucket 8 with the oldest stored
   slot (again the d1 convention; a distinct bucket 9 would need e_rec to grow and is not in the patch). How it treats them,
   label-free (out_s4_retrieval_share.txt) [M]: extension events take 7.9% (val) / 9.2% (test) / 7.1% (train) of the 16 slots
   on extended feeds (they are 12-14% of the tokens). 37% / 42% / 35% of candidates there have at least one extension event in
   their top 16. 94% of extension events are on items NOT among the feed's stored 256 events (new items).
 - Fine-tune (finetune.py) and test inference read hist_ext from the checkpoint cfg (data.hist_ext_kwargs). holdout_eval.py
   refuses extension models: the harness writes holdout predictions in train.py (--save_holdout).
 - Not combinable (asserted): --hcap, --rec_q, --rho_file, --hzcd, --aug_hist / --aug_cand, gru / din, item-ID residual, sim_bias 2.
