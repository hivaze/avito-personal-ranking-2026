---------------------------------------------------------------------------------------------------------------------
6. PROPOSALS (mechanism -> protocol -> expected gain -> kill rule)
---------------------------------------------------------------------------------------------------------------------
P1. hzcd-type parity for the popularity inputs, re-targeted at 7-24-day listings (the only private-specific lever
    found). Mechanism: section 2/4 - the private loss of the TO half sits in feeds whose positives are 1-4 weeks old
    and warm on val but cold on private (zero rate 0.30 -> 0.50); the existing it_hist_hz files restore the
    train-row zero-lift parity (0.71 -> 0.99) and were null on val (a cold/warm trade) - but the trade's private-mix
    value was never read on this axis. Protocol (CPU first, GPU only on pass): (a) re-score the 20 G3 TO members
    under the 'both' scenario (CPU replay as s02c, ~80 s/pass) and report the delta per age bucket and private-mix;
    (b) cooldown arm 'hzcd' (train rows read it_hist_hz_* in the cooldown, as INSIGHTS item 6) on roots 101-104 vs
    m02ref; readout = val, holdout, stale-val, pmix, and the 7-24 d age-bucket delta. Expected: TO member +0.0003..
    +0.0008 under private-like coverage, ~0 on val. Kill: val < -1 SE or stale-val delta <= m02ref's.
P2. Per-split transductive age-conditional popularity residual as a fine-tune extra (a_luo_resid_split,
    a_zero_rate_split; built here for val/test): val-fit standardisation keeps parity, the semantic "popularity
    relative to listings of the same age in this split" is identical on val and test, and it is the only new input
    whose private value differs from its val value by construction. Protocol: n2cpv3 + these 2 (or 4) files on >= 8
    members, 2 FT seeds; readout OOF delta (bar >= -0.0003, W3 rule) and the stale-val replay of the FT folds (ADV
    proposal 2). Expected val ~0 (probe: +0.0000/-0.0003), private 0..+0.0005. Kill: OOF < -0.0003 or no gain on
    the emulated-stale OOF.
P3. Domain-balanced train loss for the production confound (section 1c): f1/f3/f5/feed_cat_share are rewarded more
    on production feeds than on exploration feeds (ratios 1.14-1.32) while popularity is rewarded 5x less. The
    domain token handles the intercept, not the slope. Protocol: a 2-epoch paired screen with the production rows'
    loss weight annealed to 1-p_soft at the end of the cooldown (= exploration-only cooldown), read the per-family
    slope of the model's score on val (regress z(score) on z(f1), z(luo) ...) against the val label slopes above.
    Note wave-4's rho70 / rec33 already showed that removing production feeds from the cooldown hurts (-0.0035 /
    -0.0021), so this is low prior (P ~0.1); a cheaper diagnostic is the slope comparison alone (CPU, 10 min).
P4. Drop `has:pre2_fe` from the next from-scratch preset and give the Sep 6-8 train rows the LUO-cold pre2 value
    instead of NaN (a 0-cost hygiene change): it is a pure early-September date flag on train (26% of rows) and a
    constant on val/test; cAUC trRL~val50 0.631 is the single largest train/val separator among the 34 inputs.
    Expected +-0.0002; it removes a regime switch the model cannot use at inference.
P5. Fine-tune hygiene already queued (W3b/n2cpv3) stays right: the shifted FT extras are the coverage ones
    (it_hist_*_luo, seq_cv_pop, pre_idmax32(_has), pre_id_contrib_v2) and seq_cv_invd20_rk (tied-rank drift 0.532).
    A warm-only rank (NaN for cold) for seq_cv_invd20_rk and it_hist_all_luo_rk is the one remaining parity fix
    (ADV proposal 3). Expected <= +0.0003.
Not recommended (measured null here): history-structure features (h_), within-category relative features (rc_),
user x item variants (u_), content-kNN priors (k_), test-window exposure counts (xs_; also not parity-matched),
and every unused on-disk family (section 7).
