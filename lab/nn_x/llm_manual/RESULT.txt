INTERPRETATION
On this anonymised rendering, a zero-shot LLM (Opus, with tools, no external NN) does not compete with G3. It scores 0.396 against G3's 0.443
on the same 100 feeds: a paired loss of 0.048 +- 0.023 (about 2 SE), losing 57 feeds and winning 33. It is clearly better than random (+0.062),
but statistically tied with the trivial one-column heuristics: cos_max (+0.007 +- 0.016) and same-category count then cos_max (+0.002 +- 0.020).
With random rather than pessimistic tie-breaking, those heuristics reach 0.400-0.401, slightly above the LLM. The gap to G3 is similar in
every M bucket (-0.04 to -0.05) and smaller for feeds with more than one positive (-0.024 +- 0.033). The LLM matches G3 at putting a positive
at rank 1 (15% vs 14%). These are the obvious "same intent, near-duplicate" cases. It loses further down the list: it gets the first
positive into the top 5 in 32% of feeds against 45% for G3, and the mean first-positive rank is 21.7 against 14.6. All five rankers fell back
on a hand-weighted linear rule over the rendered cues: cosine, f1/f3 affinity, category recency and popularity. That is a crude, untrained
version of what G3 learns from labelled training feeds, which also has engineered item/user statistics that the text does not expose.
Ranking within one category needs calibrated weights on many weak signals. Blending the LLM ranks into G3 hurts at every weight, so there is no complementary signal to
harvest. Per-ranker differences (rankers 3 and 5 near parity, 1 and 2 about -0.09) are within noise at n=20. Conclusion: LLM manual ranking
is not a viable lever for this task, either as a standalone ranker or as a blend component, and it would not scale to 14k feeds anyway.

RANKERS' STRATEGIES (as reported by the 5 LLM rankers; each ranked 20 feeds from the text files only)
------------------------------------------------------------------------------------------------------
[Ranker 1 | feeds 1-20]
I read all 20 feeds by hand and reasoned about the patterns. I then turned that judgement into one hand-weighted rule, so every feed is treated the same way. It uses only the feed files: no trained model and no labels. The rule adds up: 1.0*f1 + 0.6*f3 + 0.5*(f2 / the feed's max f2) + 1.6*cos_to_newest_5 + 0.8*cos_max + 0.5*exp(-newest_hist_idx_same_category/8) + 0.25*(log of same-category history count, scaled within the feed) - 0.25 if the category was never seen + 0.04*log1p(popularity). I read the features this way: f3 is the same for every item of a category within a feed, but differs between users, so it looks like a user x category affinity or past click-rate. In feed 4998, c13 has f3 0.98 while c39, the most-viewed category, has 0.08, which suggests it is not just view counts. f1 looks like a finer-grained version of f3. f2 takes a few repeated values per feed with a common maximum, so it looks like a user x location match. f4 and f5 look like item-only features, so I gave them no weight. Most top picks are items in the newest category with the highest f1/f3 and cosine to the newest events. Three manual adjustments: in feed 7094 I moved c10 near-duplicates (cos 1.00) of the earlier block of repeated e4 events into the top 14. In feed 4998 I put the c39 item with the best recency cosine first. In feed 9715 I moved up the c5 item that matches the 2nd-newest event.

[Ranker 2 | feeds 21-40]
I ranked from the feed text files alone, using a transparent hand-weighted score plus manual corrections for each feed. No model, labels or other project files were used.
Score = 3.0*cos_to_newest_5 + 1.5*cos_max + 1.0*f1 + 0.6*(f2 / feed's max f2) + 0.3*f3 + 0.8*(recency-decayed share of the candidate's category in the shown history), plus a category-recency bonus (+0.25 if the category is the newest event's, +0.15 if within the last 5 events, -0.4 if the category never appears in the history), plus small terms 0.03*log1p(popularity) + 0.1*(f4+f5).
How I read the f features, inferred from patterns only:
- f3 is constant per (user, category), so it looks like user-category affinity.
- f1 looks like a finer user-subcategory affinity.
- f2 takes a few discrete levels per feed, with a dominant 'home' level; it looks like a user-location match, so f2~0 is treated as a negative.
Manual corrections:
- Lift near-duplicates (cos_max >= 0.95) of items the user acted on very recently, especially items with e2/e3/e4/e5/e6/e9 actions.
- When the newest one or two events start a new category (c29 in 12930, c20 in 2148, c3 with e9 in 12154, c40 in 115), give that category's best candidates a moderate lift, without overriding a strongly dominant recent category.
Caveat: these 20 feeds are almost all 'stay in the dominant recent category, pick the closest embedding match' cases. Within large same-category candidate sets, such as 5429 (148 candidates) and 12154 (259), the anonymised text gives few cues beyond cosine and f2, so gains over the trained ensemble are unlikely.

[Ranker 3 | feeds 41-60]
I ranked by a hand-written linear score (no trained model, no labels), computed with a small parser script over the feed files, then applied category boosts per feed by hand. Reading the data, f3 looks like a recency-weighted user-by-category affinity: it is constant per category within a feed, varies across users and follows recent engagement. f1 looks like a finer user-by-microcategory affinity (corr 0.91 with f3). f2 is a per-feed discrete value, plausibly user-by-location affinity. f4/f5 behave like item age or traffic: low values mean zero recent views, so they got no weight. Score = 0.8*f1 + 0.5*f3 + 0.3*f2 + 1.0*cos_to_newest_5 + 1.2*cos_max + 0.3*cos_max_same_cat + 0.15 if cos_max>=0.95 (near-duplicate of a viewed item) + a category recency bonus (newest event 0.25, within 3 events 0.18, within 10 events 0.10, within 30 events 0.04) + 0.25*share of the newest 20 events in the category - 0.3 for never-seen categories + 0.015*log1p(pop). Manual judgment: where a secondary category is clearly a fresh intent (newest event or recent strong e2/e3/e5 action) but is swamped by a dominant category, I added a category boost (+0.1 to +0.8) so its best items interleave near the top. This applied to feeds 12275 (c15, c13), 11190 (c22), 129 (c7), 844 (c6), 10278 (c3), 10384 (c3) and 2685 (c6). I sorted by expected relevance and did not hedge for diversity. Because history is long and candidate pools are dominated by one or two categories, most of the achievable gain is in ordering within the dominant category by similarity to recent items.

[Ranker 4 | feeds 61-80]
I made one hand-written scoring rule (no trained model), scored every candidate within its feed, and then adjusted orderings by judgement in 7 feeds. The rule gives the biggest weight to embedding similarity: cosine to the 5 newest events (1.2) and the max cosine to any history item (0.8). Next come f3, which looks like an organiser-provided user-category affinity (1.0), and f1, which looks like a finer-grained affinity because it varies within a category (1.0). I suspect this because f3 is constant per category within a feed but does not track history counts; for example, a category with no history events can have f3=0.5. Smaller weights go to f2 (0.4), recent category share with decay and extra weight for deeper event types (0.8), a newest-category bonus (+0.5 when the newest event is in that category, smaller when it is a few events back), log popularity (0.3) and f4/f5 (0.1 each, since they seem to track popularity). Candidates whose category is not in history are penalised, but less when their f3 is high. The judgement changes were: interleave two categories when the newest events show deep engagement in both, lift a strong second category above a weak tail of the main one, and demote items with f2 near 0 or very low cosine within the intent category. In practice f1/f3 plus similarity to the newest events drive most rankings; in feeds dominated by one category, ties are broken by cosine, f2 and popularity.

[Ranker 5 | feeds 81-100]
I scored every candidate with an approximate log-odds formula, using a small script that read only the feed files, then reviewed each feed by hand and overrode a few. Category prior: 0.4*ln(affinity+0.03), where affinity averages the category's share of all history events with its share of the visible history. In that share each event is weighted by exp(-idx/10), and non-e1 events count 1.5x. Then -0.3 if the category is unseen, +0.25 if it matches the newest event's category, and -0.2*ln(number of candidates in that category) as a dilution hedge. Similarity: +2.0*cos_max_to_history + 1.2*cos_to_newest_5. Features: f1, f3 and f2 look like user x category / user x context affinities (they are constant within a category in a feed, and 0.02 for unseen categories), so they get 0.55, 0.35 and 0.3; f4/f5 look item-level and get small weights (0.15, 0.1). Popularity: +0.05*ln1p(views). The prior is calibrated to the stated per-item lifts (about 1.7x for the newest event's category, about 3x penalty for unseen categories), so a strongly similar item from a secondary category can outrank a weak item from the main one. Manual overrides: lifted near-duplicates in the newest event's category when it differed from the dominant session category (3807 c32, 3336 c6, 3969 c36 already high), reordered small feeds (3680, 8446), and moved the best c33 item up in 8497.
